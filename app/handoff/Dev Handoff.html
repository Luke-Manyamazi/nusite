02 · What's built
vs. what's not

A clean line between design comp and real product
!
Read this paragraph before anything else

Every .html file in this project is a design comp. The pages render real HTML/CSS/JS, but every form submit, button, transform and payment is local-state theatre. The product behaves like the prototype looks — that's the design contract. Engineering's job is to make the wires real without changing the shape of any screen.

2.1What you can do today (design fidelity)

  • Open the landing page in any browser — fully responsive, dark/light toggle works, animations work.
  • Click through onboarding, the app shell and the engine — all transitions are real, all states are accessible.
  • Use the launch-assets hub to copy email HTML, post text, and view the PH gallery at real size.
  • Show clients/investors — the comps are demo-able.

2.2What does not work yet

  • Auth. Sign-in/up are scripted state changes. No session, no user.
  • Persistence. Nothing survives a refresh except where localStorage is used for UI prefs (theme, etc).
  • The actual transform. The engine prototype shows a canned before/after — the model isn't being called.
  • Payments. Pricing buttons don't take money. The billing page reads invoice rows from a hard-coded array.
  • File I/O. ZIP upload UI works visually; no parsing or storage.
  • Deployment. The deploy-guide screen prints a tailored guide but doesn't actually call any host's API.

04 · Data models

Minimum viable schema — extend as needed

A small, sane core. Use Postgres or your ORM of choice. JSON columns are fine for transform options and deploy metadata.

 schema.sql · core tablesPostgres · v1
create table users (
  id             uuid primary key default gen_random_uuid(),
  email          text unique not null,
  name           text,
  host_pref      text,                    -- 'vercel' | 'netlify' | …
  plan           text not null default 'starter',  -- starter|pro|premium
  stripe_customer_id text,
  founding       boolean default false,
  created_at     timestamptz default now()
);

create table projects (
  id             uuid primary key default gen_random_uuid(),
  user_id        uuid references users(id) on delete cascade,
  name           text not null,
  source_kind    text not null,        -- paste | zip | url | github
  source_meta    jsonb default '{}',    -- repo url, file count, etc.
  storage_prefix text,                    -- s3://nusite/projects/<id>/in/
  created_at     timestamptz default now()
);

create table transforms (
  id             uuid primary key default gen_random_uuid(),
  project_id     uuid references projects(id) on delete cascade,
  user_id        uuid references users(id),
  types          text[] not null,         -- ['responsive','dark-mode',…]
  options        jsonb default '{}',
  status         text not null default 'queued',  -- queued|running|done|failed
  progress       int  default 0,
  output_prefix  text,                    -- s3://…/out/
  diff_summary   jsonb,                   -- per-file change counts
  tokens_used    int,
  cost_cents     int,
  created_at     timestamptz default now(),
  finished_at    timestamptz
);

create table usage_events (        -- one row per billable transform
  id             uuid primary key default gen_random_uuid(),
  user_id        uuid references users(id),
  transform_id   uuid references transforms(id),
  period         date not null,         -- first of month
  created_at     timestamptz default now()
);

create table waitlist (
  id             uuid primary key default gen_random_uuid(),
  email          text unique not null,
  source         text,                    -- 'landing' | 'footer' | 'ph'
  utm            jsonb,
  converted      boolean default false,
  created_at     timestamptz default now()
);
⚡
Storage rule

User-uploaded source files and transform outputs go to object storage (S3 / R2), not Postgres. Database stores only IDs, metadata, and diff summaries. The README promises code is "processed securely and not stored permanently" — implement that with TTL'd S3 prefixes for free-tier users.

06 · The transform engine

The pipeline behind Stage 5 — the heart of the product

The engine prototype shows the journey; this is what the journey actually requires.

6.1Pipeline

  1. Ingest. Normalize the source — paste, ZIP, URL fetch, or git clone — into a flat {path → content} map in object storage. Reject anything outside an allow-list (.html .css .js .ts .tsx .jsx .json .md .svg) and binary assets > threshold.
  2. Plan. One LLM call. Given the file tree + selected transforms, emit a structured plan: per-file {action: keep|rewrite|delete, why}, plus any new files to create. This is the bit that prevents the model from rewriting everything.
  3. Generate. Per-file LLM calls, in parallel where independent. Pass the file content + plan entry + relevant siblings (e.g. when porting CSS to Tailwind, pass the styles file alongside).
  4. Reconcile. Detect broken refs (an img src that no longer exists), missing imports, type errors. One repair pass.
  5. Diff. Compute per-file diffs and a one-line summary per file. Persist as diff_summary on the transform.
  6. Deploy guide. Templated markdown per host, parameterised with the project's framework guess (Vite, Next, plain static).

6.2Run-time shape

Queue
Background worker (BullMQ on Redis, or Cloudflare Queues). The API enqueues; the worker runs the pipeline. Never run an LLM call in an HTTP request handler — they time out and the user re-submits.
Streaming
SSE from API to client. Worker publishes progress events to Redis; API subscribes and forwards. Fall back to polling.
Concurrency
One transform per user at a time on Starter / Pro. Up to 3 in flight on Premium. Avoids accidental DOS via the paste box.
Cost ceiling
Hard cap per transform (tokens × price). Bail with a friendly error if a transform projects to exceed it — usually a sign of an oversized input.

6.3Model choice

Start with one model (Anthropic claude-sonnet-X or equivalent). Build the prompt-cache to keep the file-tree context cheap across the per-file calls. Don't over-engineer model routing in v1 — pick one and tune the prompt.

★
Diff trust is product-critical

The engine prototype's diff screen is doing the heavy lifting of "would I actually ship this output?" In production, never show a green-light "done" until the per-file diffs render and at least the headline files have a summary the user can scan. If they can't see what changed and why, they won't deploy it, and you lose the conversion.

09 · Stack recommendation

One sensible default per layer · swap as you like
FrontendSSR optional

Next.js · 14+ App Router

The landing page can stay as a static HTML file, hosted as-is. The app + engine + billing pages get rebuilt in Next so we can stream from server actions and protect routes per plan.

Co-locate handlers with the frontend, get end-to-end typing for free. The long-running transform jobs aren't in API routes — they're in the worker.

Alts: Hono on Cloudflare Workers, Fastify in a separate package
WorkerLong-running

Node + BullMQ on Fly.io

A tiny always-on service that consumes the transform queue. One small VM is enough for launch.

Alts: Railway, Render, Hetzner CX22 if you want the cheapest possible
DatabasePostgres

Serverless Postgres with branching. Drizzle gives you typed queries with no ORM-as-DSL weirdness.

Alts: Supabase (also gives auth + storage), Prisma if your team prefers it
Object storageSource + output

Cloudflare R2

S3-compatible, no egress fees. Critical when users download transform-output ZIPs.

Alts: AWS S3, Backblaze B2
AuthMagic link

Magic-link in 30 minutes. Roll your own only if "no SaaS for auth" is a value, not a constraint.

Alts: Auth.js (NextAuth), Supabase Auth, WorkOS
PaymentsSubs + invoices

Hosted checkout + customer portal. The portal gives you billing UI for free — you only build the "current plan" summary, which is already designed in NuSite Billing.html.

Alts: Paystack (ZA-friendly), Lemon Squeezy (MoR — handles VAT)

Resend · + Loops

Resend for the lifecycle emails (the Stage 7 templates), Loops for the marketing list. Set DKIM/DMARC on nusite.app before launch day.

12 · Open questions

Decisions still owed before build can finish
  1. Entity for Stripe. Camluk Technologies (Pty) Ltd is a ZA entity — will Stripe work for our jurisdiction, or do we route global cards through Paystack? Decision affects pricing copy on the landing page.
  2. Free-tier abuse. 5 transforms/month/account is gameable with throwaway emails. Do we require email verification before the first transform? Captcha on signup?
  3. Storage TTL. The README promises "not stored permanently." Concretely: delete project source after 24h on Starter, 7 days on Pro, 30 days on Premium? Audit before launch.
  4. GitHub app scope. Read-only on selected repos vs. install-wide. We've designed for selected — confirm before submitting the GitHub App listing.
  5. Per-transform pricing for Premium custom prompts. "Unlimited" with custom prompts can run up serious LLM bills. Soft cap at $X/month with a friendly "you've used a lot, here's why" email at 80%?
  6. Region. Single region (eu-west / us-east) or multi? Single is simpler; latency is fine for a batch product. Pick one.
